# 棚卸し（雑貨）

雑貨・金券・たばこなど、決算の「雑貨棚卸」を金額ベースで行うための棚卸し。
これまで Access（まとめ.mdb / 棚卸チーズ用.mdb）で出していた理論在庫と差異を WMS で扱う。
出力の単位は旧Accessと同じ中分類。

## 既存の棚卸しとの関係（独立性）

- メニューは「在庫管理 > 棚卸し（雑貨）」。既存の「棚卸し」とは別リソース・別画面・別テーブル。
- 既存の棚卸し（`WmsInventoryCount*` / `app/Services/InventoryCount/*` / 既存ブレード）は1行も変更していない。
- 読み取りで共用するのは `InventoryCountLedgerBalanceService::balancesByItem`（倉庫×商品の受払残）だけ。
  在庫管理あり商品の理論数は、既存棚卸しの「理論在庫更新」と同じ値になる。
- 権限は既存の棚卸しと同じ `wms.wms-inventory-count.*` を使う（権限マスタの追加は不要）。
- 在庫・伝票への書き込みはしない。HANDY入力もない。調整伝票は差異表をもとに従来どおり基幹で起票する。

## 対象

作成時に2種類の対象を選ぶ。既定値は `config/wms_sundry_inventory.php`。

- 対象中分類: 既定 2040 / 2041 / 2043 / 2044 / 2047 / 2051 / 2052。
  在庫管理ありの商品は数量明細、在庫管理なしの商品は中分類ごとの金額明細になる。
  チーズ 2026（二の宮店・越前店）などは作成時に追加する。
- 金額で棚卸しする大分類: 既定 1004 雑貨。
  選んだ大分類は、対象中分類に無い中分類（2042 雑種・2045 ハーブなど）も含めて金額明細を作り、
  その合計を在庫金額報告書（大分類単位）と突き合わせる。
- 対象外の商品は、詳細画面の「商品追加」で商品CDから個別に追加できる（明細に「追加」と表示）。
  在庫管理なしの商品を追加すると、その中分類の金額明細が増える。

明細は2種類。

- 数量明細（在庫管理あり）: 対象中分類の商品のうち、倉庫に在庫行があるか受払残が0でない商品。商品ごとに1行。
  OWNEDセット親・容器は対象外。
- 金額明細（在庫管理なし）: 中分類ごとに1行。その中分類の在庫管理なし商品すべて
  （代表コード 410000 / 470000 など）が対象。

## 計算

### 数量明細

- 理論数 = 受払終了日の終了時点の受払残（2026-05-06 期首残 + 受払）。
- 原価 = 棚卸し日時点で有効な `item_prices.cost_unit_price`（開始日 <= 棚卸し日 の最新行）。
  基幹の月末原価スナップショット（`item_cost_snapshots`）と同じ採用ルール。
- 理論金額 = 理論数 × 原価、実棚金額 = 実棚数 × 原価、差異金額 = (実棚数 − 理論数) × 原価。

### 金額明細

旧Access（Ｔ３在庫）と同じ式を、中分類ごと・日付指定で計算する。
受払の取り方は、基幹の月次在庫確定（`/stats/monthly-stock-confirmation`、`MonthlyStockAmountValuation`）の非管理品と同じ。

```
理論金額 = 前残金額 + 仕入 + 移入 − 移出 − 売上原価 + 調整
```

#### 前残金額

次の順で決める。画面とExcelに「前残の出所」として表示する。

1. 前回棚卸の実棚: 同じ倉庫・中分類の、前回確定した棚卸し（雑貨）の実棚金額。基準日 = その棚卸し日。
2. 旧システム残高: 移行元Oracle（Ｔ３在庫）の最終残高。基準日 = 旧システム最終日。
   `database/data/sundry_inventory/nonmanaged_opening/{基準日}.csv`（`warehouse_code,category2_code,amount`）。
   CSVに倉庫はあるが中分類の行が無い場合は 0円。
3. 未設定: どちらも無い倉庫は、基準日 = `default_opening_date`（2026-05-05）、前残金額 = 0。画面で手入力する。

- 「理論在庫更新」のたびに取り直す。
- 前残金額や基準日を画面で直した行は「手入力」になり、理論在庫更新でも戻さない。
  更新時に「手入力した前残金額も自動の値（前回棚卸の実棚・旧システム残高）に戻す」を選ぶと戻る。

##### 旧システムと新システムの境目

旧システムは 2026-05-05 まで、新システムは 2026-05-06 から。
そのため旧システム残高は 2026-05-05 時点（Ｔ３在庫 管理年月=202605 の残高）とし、受払は新システムの 5/6 以降だけを集計する。
在庫管理あり商品の理論数（2026-05-06 期首残 + 受払）と同じ境目になる。

- 新システムにも 5/1〜5/5 の仕入伝票が移行されているが、これは旧システム残高に含まれているので集計しない
  （Ｔ３在庫 202605 の仕入額と、移行済み仕入伝票の金額が倉庫×中分類で一致することを確認済み。大分類7=空容器を除く）。
- 5/1〜5/5 の小売POS売上・移動は新システムに無い（POS・移動は 5/6 から）。旧システム残高側に含まれる。
- 5/5 以前の日付で、5/6 以降に新システムへ入力された伝票は集計しない（無視する。2026-10-04 決定）。
  ローカルDBでは在庫管理なし商品で4件（華むすびの蔵センター 中分類2041 の仕入 22,380円〈5/1付・5/29入力〉、
  特販課 中分類2015 の売上3件）。

`2026-05-05.csv` は、移行元Oracleから次の集計で作成した（参照のみ。0円の行と大分類7=空容器は除外。
中分類コードは 2000 + 旧2桁コード。138行・17倉庫）。

```sql
SELECT TRIM(t."店舗ＣＤ"), SUBSTR(m."分類ＣＤ", 1, 2) AS c2,
       SUM(NVL(t."前残金額",0) + NVL(t."仕入額",0) + NVL(t."移入額",0) - NVL(t."移出額",0)
           - NVL(t."売上額",0) - NVL(t."払出額",0) + NVL(t."調整額",0))
FROM HANA."Ｔ３在庫" t
JOIN HANA."Ｍ２単品" m ON m."単品ＣＤ" = t."単品ＣＤ"
WHERE t."管理年月" = '202605' AND m."在庫管理区分" = '0'
GROUP BY TRIM(t."店舗ＣＤ"), SUBSTR(m."分類ＣＤ", 1, 2)
```

裏取り:

- 同じ集計を 202603 で行うと旧Accessの出力（PDF）と全行一致する。
- 202605 の前残金額は、202604 の残高と全キーで一致する（月次繰越が正しい）。
- 202605 の売上額は、Ｔ２売上（5/1〜5/5、在庫管理区分=0）の原価金額の合計と一致する
  （本店 中分類41 = 2,698 / 47 = 225、二の宮店 41 = 2,850、越前店 41 = 6,369 で確認）。
  Ｔ３在庫に 202606 以降の行は無い。

#### 受払

- 集計期間は「基準日の翌日」〜「受払終了日」。
- 仕入 / 移入 / 移出 = 実取引金額（`trade_items.amount`）。移動は `COALESCE(picking_date, process_date)` で判定。
- 売上原価 = (EARNING売価 + 小売POS売価) × 分類原価率（`item_categories.cost_rate`、小→中→大分類の順）。
- 調整 = 調整プラグ対象の小分類（値引・金券・送料など、`plug_subcategory_codes`）の売上原価。売上原価を同額で相殺する。

#### 在庫金額報告書との突合（大分類別・参考）

「金額で棚卸しする大分類」ごとに、在庫金額報告書（`stats_monthly_stock_amount_reports`）から求めた理論金額と、
中分類明細の理論金額の合計を並べて表示する（金額明細タブの下、Excelの金額明細シートの下）。

```
非管理品の月末残高   = 報告書の月末金額(closing_amount) − 在庫管理あり商品の月末評価額
在庫管理あり評価額   = Σ COALESCE(確定実在庫, 月末計算数量) × 月次原価(item_cost_snapshots)
報告書ベース理論金額 = 非管理品の月末残高 + 月末の翌日〜受払終了日の受払（大分類で集計）
差                  = 中分類明細の理論金額 合計 − 報告書ベース理論金額
```

- 受払終了日以前に月末を迎えた最新の報告書を使う（例: 受払終了日 10/6 で 9月分が未作成なら 8月末）。
- 報告書が無い、または月次数量・月次原価が無い月は「報告書なし」と表示する。
- 突合は表示だけで、理論金額・差異金額には影響しない。

- 在庫金額報告書の在庫管理なし商品は、4月末残高に新システムの5月以降の伝票を積んだもので、
  旧システム期間（5/1〜5/5）の売上原価・移動を含まない。その分は差に出る。
  基幹の5月前残（`nonmanaged_prev/2026-05.csv`）は旧システムの4月末残高と同額で、5/5 残高との差が
  倉庫ごとに 5/1〜5/5 の受払と一致する（大分類4: 本店 698,420 − 695,497 = 2,923 など15倉庫）。

ローカルDB（hana_local、8月末の報告書、受払終了日 10/4）での確認結果（大分類1004）:

| 倉庫 | 差 | うち 5/1〜5/5 の旧システム受払 |
|---|---|---|
| 本店 | −2,923 | −2,923 |
| 二の宮店 | +2,038 | −3,075 |
| 坂井店 | −7,121 | −6,756 |
| 敦賀店 | −7,848 | −7,848 |
| 越前店 | −9,108 | −7,199 |
| 小浜店 | +9,085 | −5,475 |
| 華むすびの蔵センター | −30,948 | −39,548（5/29入力の 5/1付仕入 22,380 を含む） |

残りの差（二の宮店 +5,113 / 坂井店 −365 / 越前店 −1,909 / 小浜店 +14,560 / 華むすびの蔵センター +8,600 など）は
4月末残高ベースで比べたときからある差で、8月末時点と 10/4 時点で同額。原因は未確認。

## 操作

1. 「棚卸し（雑貨）作成」で倉庫・棚卸し日・対象を選ぶ。棚卸し日までの受払で理論値を作る（未来日なら当日まで）。
2. 「指示書」をPDFで出し、実棚数を手書きする。
   最終ページに在庫管理なし（中分類ごと）の実棚金額の記入欄が出る。
3. 棚卸し日の受払が入り切ったら「理論在庫更新」で受払終了日を棚卸し日にして再計算する。実棚の入力値は変わらない。
4. 詳細画面で実棚数（数量明細）と実棚金額（金額明細）を入力し「反映」。
   未入力は差異に含めない。数量明細は「未入力0」で一括して0にできる。
5. 「集計」と「差異表Excel」で差異金額を確認する。
   Excel は 集計 / 数量明細 / 金額明細 / 非管理品仕入（旧「雑貨代表コード仕入先」）の4シート。
6. 「確定」で入力を締める。「確定解除」で入力中に戻せる。
   確定した実棚金額は、次回の棚卸し（雑貨）の前残金額になる。

## 種類「量り売り」（2026-10-09 追加）

量り売り焼酎の棚卸し。これまで Access（量り売り棚卸.mdb）で出していた差異表を置き換える。
作成時に種類で「量り売り」を選ぶと、雑貨とは別の棚卸しデータになる（メニュー・一覧・権限は共通）。
種類が雑貨の棚卸しの動きは変えていない。

### 旧Accessとの対応

| 旧Access | 内容 | WMS |
|---|---|---|
| Ｍ２単品（ローカル表） | 対象23商品（単品CD 129002〜129024）と出力順 | `config/wms_sundry_inventory.php` の `weighed_item_codes`（並びが出力順） |
| Q_01 / Q_02 | 理論在庫数 = 前残 + 仕入 + 移入 − 移出 − 売上 − 払出 + 調整（Ｔ３在庫・月単位）、仕入単価 | 理論数 = 受払終了日の受払残（雑貨の数量明細と同じ計算・日付指定）、原価 = 棚卸し日時点の `item_prices.cost_unit_price` |
| Q_03 | 前回棚卸日の翌日〜今回棚卸日の売上数量（Ｔ２売上） | 期間売上数量（下記） |
| Q_05 | 実棚数（カメ）・実棚数（QT）の手入力、差異数、差異金額 | 詳細画面の「量り売り明細」タブ。実棚数 = カメ + QT |
| Q_06 | 店舗へ送る表（カメの実棚が入っている行） | 差異表Excel の「差異表」シート（実棚を入力した行。0 と入力した行も出す） |
| Q_08 | 店舗計（差異・売上数量・ロス 4%） | 「集計」タブ、差異表Excel の「店舗計」シート |
| Q_10 | 売上数量の一覧 | 差異表Excel の「全明細」シート |

- 数量は 100ml 単位（量り売り商品は在庫管理ありで、在庫・POS売上とも 100ml 単位で持っている）。
- 対象は設定の商品のうち、倉庫に在庫行があるか受払残が 0 でない商品。設定に無い商品は「商品追加」で追加できる（在庫管理ありの商品のみ）。
- 金額明細（在庫管理なし）は作らない。

### 期間売上数量

作成時に「期間売上の開始日（前回棚卸日の翌日）」を入力する。開始日〜受払終了日の売上数量を明細に持つ。
開始日は「理論在庫更新」で変更できる。

- 2026-05-06 以降: 理論数と同じ元データ。小売POSの在庫引当（`ret_pos_stock_applications.quantity`）+ 売上伝票（EARNING、返品はマイナス）。
- 2026-05-05 以前: 日別売上の統計（`stats_item_warehouse_daily_sales.sales_piece_qty`。旧システムの売上を取り込み済み）。

確認（ローカルDB）:

- 2026年4月の期間売上は、トスバックのＴ３在庫 202604 の売上数と一致（本店・二の宮店の 129002 / 129007 / 129012）。
- 5月（境目をまたぐ月）は統計の月合計と一致、5/6 以降は POS の数量と一致（本店 129002）。
- 卸売上のある倉庫（小浜店）は、POS + 売上伝票の合計が統計の売上数量と一致。

### 差異・ロス

```
差異数   =（カメ + QT）− 理論数
差異金額 = 差異数 × 原価
ロス数量 = 期間売上数量 × ロス率（商品ごとに四捨五入。ロス率は weighed_loss_rate = 4%）
ロス金額 = ロス数量 × 原価
ロス申請後差異金額 = 差異金額 + ロス金額
```

- 集計と店舗計は、実棚を入力した明細だけを合計する。
- 旧Accessの Q_08 は、ロス申請後差異金額の実棚数にカメだけを使っていた（QT が入っていない）。WMS はカメ + QT の合計を使う。
- 「未入力0」は、未入力の明細をカメ 0 として登録する。

### 指示書・Excel

- 指示書PDF: 商品CD・商品名・理論在庫数・実棚数（カメ）・実棚数（QT）の記入欄。
- 差異表Excel: 差異表（店舗へ送る表）／店舗計／全明細 の3シート。

### 追加した列（マイグレーション `2026_10_09_000000_add_weighed_kind_to_wms_sundry_inventory_count_tables.php`）

- `wms_sundry_inventory_counts`: `kind`（sundry / weighed。既定 sundry）、`sales_from_date`
- `wms_sundry_inventory_count_items`: `display_order`、`counted_quantity_jar`、`counted_quantity_reserve`、`period_sales_quantity`

## テーブル

- `wms_sundry_inventory_counts`: ヘッダー（対象中分類、金額で棚卸しする大分類、報告書との突合結果、
  受払終了日、ステータス counting / confirmed / cancelled）
- `wms_sundry_inventory_count_items`: 数量明細
- `wms_sundry_inventory_count_amounts`: 金額明細（大分類・中分類、前残とその出所、受払内訳、理論金額、実棚金額）

マイグレーション: `2026_10_03_000000_create_wms_sundry_inventory_count_tables.php`（新規テーブル3本のみ）。

## 注意点・未対応

- 旧システム残高CSVは 17倉庫分。CSVに無い倉庫は前残0円・「未設定」で作る。
- チーズ 2026 の在庫管理なし商品（代表コード 260000）は、旧システム残高がマイナスの店舗がある
  （二の宮店 −1,149,283 / 越前店 −543,386）。Ｔ３在庫の履歴では仕入が一度も無く、2018〜2024年に入力された
  調整額の累計（二の宮店 −907,040 / 越前店 −404,186）と過去の売上原価が積み上がったもので、
  2024年9月以降は調整が無く、売上原価が年0〜2千円動いているだけ。
  旧Accessのチーズ棚卸は単品（261*/262*、数量≠0）単位で、この代表コードの残高は出力していなかった。
  対象中分類に 2026 を加えると、この残高が金額明細の前残に出る（扱いは確認中）。
- 金券 2052 の在庫管理なし商品（代表コード 520000）は、旧システム残高がマイナスの店舗がある
  （坂井店 −23,100 / サンドーム前店・プラザ店 −6,600 / ヴィオ店・敦賀店・江守店 −3,300）。5/1〜5/5 の売上原価。
  旧システムでは毎月、売上額と同額の調整額を入れて月末残高を 0 にしていた（2025年4月・5月、2026年4月で確認）。
  5月は 5/5 で止まったため調整が入っていない。新システムでは金券は調整で相殺し残高を持たない（扱いは確認中）。
- 調整伝票の自動作成（基幹連携）。
- 量り売りは種類「量り売り」で対応（上記）。全店分をまとめて作成・出力する機能は無い（倉庫ごとに作成する）。
- 既存棚卸しのような複数回カウント・HANDY入力・ロケーション別明細。
