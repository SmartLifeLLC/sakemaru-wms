# 手動発注・JX取消とカレンダー生成の運用

## 旧管理者メニューの候補生成を非表示

「発注・移動候補生成」画面の旧「管理者メニュー」（移動候補生成・仕入先別発注候補生成）をアクション登録から外す。実行ログの同じ計算を呼ぶ「再実行」も非表示・無効とし、旧ウィザードの候補削除・ジョブ起動をLivewireの公開メソッドから外す。履歴・送信詳細・エラー詳細と、通常の販売実績からの候補生成は維持する。

旧計算は自動発注ONの倉庫と旧商品設定に依存し、全倉庫OFF時に空の `IN ()` で失敗する。初回リリースで旧商品設定も初期化済みのため、ボタンを戻すだけで再開しない。再利用時には、倉庫ON/OFFとの分離、対象0件の安全な終了、商品設定と数量の妥当性を確認する。旧計算サービス・ジョブ・CLI自体の改修は今回の対象外。

## 倉庫カレンダー一括生成の利用停止

`wms:generate-calendars` は利用停止。倉庫・期間の指定有無によらず、DBにアクセスせず日本語の案内を表示し、終了コード `1` を返す。実行を許可するオプションは設けない。

既存の「倉庫カレンダー」画面による日付編集は引き続き利用できる。既存の日付計算、配送コース、休日参照処理は変更しない。この停止はコマンド入口に対するもので、開発用「テストデータ生成」のサービス直接呼出しは変更しない。

再利用する場合は、コードを戻すだけで有効化しない。以下を確認してから別途改修する。

- 対象倉庫を自動発注ON/OFFから分離する。全倉庫OFFでも、営業日設定の必要性は変わらない。
- 休日設定が未登録の場合に、日曜・祝日などの既定値を推測して作成しない。未登録は処理を保留する。
- 登録済み日付と手動編集日を保護する。既存サービスは手動編集日以外を上書きし得るため、差分確認が必要。
- 倉庫と期間を限定した変更予定一覧を出し、入荷日・出庫日の変更を確認してから反映する。
- 定期実行は現在コメントアウトされている。再開する場合は、cron・画面・サービス直接呼出しを含めて実行経路を再点検する。

## 手動発注の確定取消

| 現在の状態 | 操作 |
| --- | --- |
| JX未生成 | 従来どおり「確定取消」。未入荷の入荷予定を削除し、候補を承認済みに戻す。 |
| JX生成済み・送信待ち | 「JX送信ファイル」で対象ファイルの「生成取消」後、発注の「確定取消」を行う。 |
| JX送信中・送信済み | 確定取消不可。送信結果を確認し、既存の訂正手順で対応する。 |
| JX送信エラー・結果不明 | 確定取消不可。送信先への到達状況を照合し、既存の復旧・訂正手順で対応する。 |

JX生成済みの発注で先に「確定取消」を押した場合は、日本語で上記の順序を案内する。候補・入荷予定・JXの紐付け・生成記録は変更しない。取消直前に候補をロックして最新の状態を確認する。

JXの「生成取消」はファイル単位であり、同じファイルの他商品にも適用される。このため、商品単位の確定取消から自動でJXファイルを取り消さない。必要な商品を修正・再確定した後は、既存画面でJX未生成の商品を確認して再生成する。

「生成取消」によって元のJXは取消済みとなる。手動候補の再生成時は、既存の二重生成防止処理がこの状態を確認し、元の生成記録を置き換えて再生成を許可する。送信待ち・送信中・送信済みの記録を無条件に削除しない。

自動発注の生成済み候補、およびJX生成処理中の候補を変更できない既存の制御は維持する。修正前に既に紐付けが切れたデータは、このパッチでは自動補正しない。元のJXと候補の照合が必要。

## 強制終了後の手動JX復旧

`wms:resolve-auto-replenishment-claim` に手動発注用の `--manual` を追加する。既存の自動発注用分岐は維持する。ここで「登録済み」とは、JX文書・候補の紐付け・伝票番号割当がDBに登録された状態であり、問屋への送信とは別の工程。

通常の例外では未登録の生成記録（`BUILDING`）を `finally` で解除する。エラーログの通知に失敗しても解除を試みる。強制終了、メモリ不足、プロセス終了を伴うタイムアウト、解除時のDB障害などでは後処理が完了せず、記録が残る可能性がある。時間経過による自動解除は行わない。

### 操作手順

1. ワーカーの処理終了と、対象発注のJXファイル・生成ログ・送信結果を確認する。
2. 候補IDと復旧担当者のユーザーIDで照合する。以下は照合結果の表示のみで、DBのデータを変更しない。

```bash
php artisan wms:resolve-auto-replenishment-claim <候補ID> --manual --actor=<担当者ID>
```

3. 表示された候補・入荷予定・ファイルを確認する。JX生成結果が未登録で、外部に送付されていないことを確認できた場合だけ、表示された `claim_token` を指定して適用する。

```bash
php artisan wms:resolve-auto-replenishment-claim <候補ID> --manual --apply \
  --actor=<担当者ID> --claim-token=<照合結果のclaim_token> \
  --reason="ワーカー停止後、保存ファイルと送信ログで未送信を確認" \
  --confirmed-unpublished
```

4. 成功後は既存の発注画面で対象候補のJX生成を再実行する。発注の再確定や入荷予定の作り直しは不要。

定時生成の実行記録（`wms_jx_order_generation_runs`）が強制終了で `RUNNING` のまま残った場合、このコマンドはその記録を変更しない。スケジュールの自動再開まで復旧したとは判断せず、対象を確認して画面から再生成する。

### 解除する条件と範囲

- 復旧担当者が配備顧客の有効なユーザーで、発注データファイルの閲覧・編集権限を持つこと。
- 対象が同じ顧客の確定済み手動EOS候補で、自動発注実行明細を持たず、送信待ちであること。
- 通常生成と同じ候補単位の排他ロックを取得し、同一DB接続で候補と生成記録を照合できること。稼働中・DB障害・接続変更では解除しない。
- 対象が `BUILDING`、JX紐付けなしで、発注内容・入数が生成開始時と一致し、入荷予定の状態と数量も一致すること。
- 関連JX文書・伝票番号割当・送信履歴・発注ファイルに、未取消・送信済み・配布済み・参照切れなどの矛盾がないこと。
- 適用直前にも対象識別子・状態を確認し、対象1件の生成記録の解除と監査記録を同じトランザクションで行う。監査記録には担当者・理由・照合内容を残す。

同じ生成処理の別候補が登録済みでも、そのデータは変更しない。発注・入荷予定・採番連番・S3ファイルも変更しない。生成内容とS3のUUID保存先は完全には対応付いていないため、DB照合だけで未送信を断定しない。保存ファイルとログの有人確認ができない場合は適用しない。

### エラーとSlack通知

残った生成記録によって再生成が拒否された場合は、既存画面に発注候補IDと照合を促す日本語のエラーを返し、`Order file generation failed` をエラーレベルで記録する。本番で確認した既存のログ設定（`stack_prd`）は、このエラーを通常ログとSlack通知の対象にする。Slackへの実際の到達はネットワーク・通知先の稼働に依存する。

**毎分監視・定期巡回・新しいスケジュールは追加しない。** 強制終了した瞬間はエラー処理が動かないため即時通知を保証しない。再生成を操作した時点で残留記録を検出する。再操作がない間の検知は今後の運用検討とする。
